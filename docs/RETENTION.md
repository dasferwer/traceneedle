# Граница поддерживаемой истории

Автоматического удаления нет. `SUPPORTED_LATE_MINUTES=0` и
`HISTORY_RETENTION_MINUTES=0` по умолчанию сохраняют прежний приём старых данных
и отключают очистку. Обе настройки читаются API и worker; передавайте им одинаковые
значения. Они должны быть целыми неотрицательными числами. Для включённого retention
нужны `late > 0` и `history >= late + 5`: пять дополнительных минут сохраняют
контекст обычного детектора новых шаблонов. Ошибка конфигурации останавливает
инициализацию до подключения к БД.

Технический пример для короткой демонстрации: late=60, history=120, пакет=1000.
Это не срок хранения пользовательских данных и не бизнес-политика. Настройки
выбирает оператор. Размер пакета ограничен 1–10000 строками **каждой** из пяти
таблиц; один вызов удаляет максимум `5 * batch_size` строк, без каскадного удаления.

## Приём и воспроизводимость

Нижняя граница нового события/traffic/new comparison — максимум `now - late`
(если late включён) и сохранённого `retained_since`. Точная граница включается,
более старые данные получают HTTP 422. Сравнение допускается только когда начала
обоих окон попадают в поддерживаемую историю. Окна полуоткрытые `[start,end)`.
Идентичный повтор **сохранившегося** события или comparison остаётся идемпотентным.
После удаления строки UUID уже не является бессрочным журналом дедупликации;
повтор старого содержимого ниже границы всё равно отклоняется.

Каждое неархивированное сравнение закрепляет все события (включая INFO/WARN и
необработанные записи) и traffic внутри обоих окон независимо от их возраста.
Старые поздние события и исправления traffic именно в этих закреплённых окнах
по-прежнему принимаются. Его regressions/history никогда не удаляются очисткой.
Повторная оценка этих окон сохраняет результат, а поздние данные и correction
могут добавить новую ревизию с прежними правилами. Это явное продление поддержки
для выбранных сравнений, поэтому забытые активные сравнения увеличивают хранение.

`POST /comparisons/{id}/archive` завершает сравнение: перед заморозкой выполняется
последняя оценка; необработанные события в его окнах дают 409. Повтор archive
идемпотентен. Новые логи/traffic больше не меняют его историю. После архивирования
окна перестают быть закреплёнными; за пределами обычной поддержки поздние записи
получают 422. Raw events/traffic могут быть удалены уже ближайшей очисткой;
сама история сравнения становится кандидатом через `history` минут **после archive**.
Удаление истории, regressions и comparison идёт отдельными пакетами; у истёкшего
архива во время этой очистки GET может показывать частично удалённую историю,
после завершения — 404. Для архивов за пределом retention replay не обещается.

## Dry-run и применение

Все операции требуют обычный API-ключ. Сначала получите состав кандидатов:

```sh
curl -sS -H "X-API-Key: $API_KEY" -H 'Content-Type: application/json' \
  "$API_URL/maintenance/cleanup" -d '{"batch_size":1000}'
```

`dry_run` по умолчанию `true`: нет удалений и сдвига watermark. Ответ содержит
`enabled`, `cutoff`, `supported_since`, ключи кандидатов в `items` и признак
дополнительных **сейчас допустимых** строк в `more` для каждой таблицы.
Порядок фиксирован временем и полным первичным ключом. Preview показывает
ограниченный очередной пакет, а не выгружает всю историю в память.

Для применения отправьте `{"batch_size":1000,"dry_run":false}`. План строится
до любого удаления, поэтому при неизменных данных и cutoff совпадает с preview.
В реальном времени cutoff движется; dry-run не является токеном подтверждения
конкретного snapshot. Повторяйте вызовы, пока все `items` не станут пустыми:
удаление history открывает eligibility regressions/comparison только следующему
вызову. `more=false` само по себе ещё не означает завершение зависимых этапов.

Очистка, ingest, worker, traffic и archive сериализуются advisory locks в одном
порядке; удаления и монотонное обновление `retained_since` атомарны. После apply
снижение/выключение retention не объявляет удалённую историю снова полной.
Необработанные события никогда не удаляются. При сбое транзакция откатывается.

Drain state, groups, incidents и компактные `group_versions` сохраняются:
`last_seen` не позволяет старому событию сдвинуть уже ушедшее окно назад,
`first_error` не позволяет удалению старого ERROR объявить знакомую группу новой.
Существующая БД получает эти метаданные из сохранившихся событий при init.
Это ограничивает raw history, а не весь диск БД: метаданные растут по группам и
версиям, закреплённые окна и очередь требуют наблюдения оператора.
Очистка данных из сообщений и полноценное удаление всех следов пользователя
не реализованы.

## Проверяемый сценарий

`scripts/verify_retention.py` требует localhost API/PG и отдельную схему
`runtime_p2*`, проверяет, что API и PG видят один fixture. Используйте новые БД/
схему, согласованные настройки API/worker late=60/history=120 и работающий worker:

```sh
API_URL=http://127.0.0.1:60260 API_KEY=local-demo-key \
DATABASE_URL='postgresql://demo:demo@127.0.0.1:60257/traceneedle?options=-csearch_path%3Druntime_p236' \
uv run python -m scripts.verify_retention
```

Сценарий ускоренно старит только свой fixture на сутки, проверяет сохранение
оснований при cleanup, поздний baseline и traffic correction с ревизиями 1/2/3,
архивирование и 422, затем очищает 10000 синтетических обработанных строк.
Seed=360, batch=1000, concurrency=1. В локальной проверке 09.10.2026 на
macOS arm64/Python 3.12.13/PostgreSQL 17: 10000 удалений, 11 HTTP вызовов включая
пустой, 2,204 с суммарно, максимум пакета 0,270 с. RSS драйвера 53706752 байт
(macOS ru_maxrss). В память драйвера входит fixture; RSS сервера/PG этим числом
не измерен. Это локальный замер, не SLA. Тесты отдельно проверяют точные границы,
pending, архивную пакетную очистку, watermark и миграцию метаданных.
