# TraceNeedle

Приём логов, выделение шаблонов Drain3, группировка ошибок и поиск новых
повторяющихся проблем после изменения версии приложения. События связываются
по `trace_id`; векторный поиск показывает похожие группы для расследования.

## Возможности

- Повтор события с тем же UUID и содержимым не создаёт вторую запись;
  другое содержимое под прежним UUID возвращает 409.
- До 1000 событий в запросе. Очередь ограничена 10 000 необработанных событий;
  при перегрузке возвращаются 429 и `Retry-After: 1`.
- PostgreSQL хранит события и состояние Drain в одной транзакции. После ошибки
  пакет откатывается целиком; перезапуск восстанавливает идентификаторы кластеров.
- Маскируются UUID, значения request/user/job/connection ID и длительности.
  Числовые HTTP-коды сохраняются. Порог сходства Drain — 0,85.
- Пять ERROR-событий одной новой группы и версии за пять минут создают инцидент.
  INFO/WARN не создают тревогу; группа, уже известная по ERROR в другой версии,
  не считается новой.
- Окно заканчивается максимальным временем события группы и версии. Поздние
  события внутри этого окна учитываются. Более старые сохраняются, но не создают
  ретроспективные тревоги за уже ушедшее окно.
- Статистика версий показывает число событий, ошибок и групп. `trace_id`
  связывает события разных компонентов с сохранением порядка по времени.

Стек: Python 3.11+, FastAPI, RabbitMQ, PostgreSQL/pgvector, Drain3, scikit-learn.
Векторы — локальный `HashingVectorizer` символьных n-грамм размерности 64.
Это лексическое представление, а не нейросетевая семантическая модель.
Похожие векторы помогают исследовать группы, но автоматически их не объединяют.

## Запуск

```sh
docker compose up --build -d
curl -H 'X-API-Key: local-demo-key' http://localhost:8096/health
```

Для размеченного демонстрационного потока нужны `uv` и зависимости:

```sh
uv sync --frozen
uv run python -m scripts.evaluate
```

Скрипт создаёт уникальный сервис, отправляет 24 синтетических события трёх классов
и измеряет Adjusted Rand Index группировки, количество инцидентов и задержку
от первого события до обнаружения. Сценарий не является оценкой на реальных логах.

## API

Все запросы требуют `X-API-Key: local-demo-key`. Форматы: `/docs`.
`POST /events` принимает объект `events` со списком записей:

```json
{
  "id": "00000000-0000-4000-8000-000000000001",
  "service": "orders",
  "version": "v2",
  "happened_at": "2026-09-24T12:00:00Z",
  "level": "ERROR",
  "message": "DB_TIMEOUT request=123 host=primary",
  "trace_id": "demo-trace"
}
```

Время должно иметь часовой пояс и не уходить более чем на минуту в будущее.
Для демонстрации используйте актуальные метки времени, как в `scripts/evaluate.py`.

- `GET /groups?after=0&limit=100` — шаблоны групп.
- `GET /groups/{id}/similar` — пять ближайших групп по косинусному расстоянию.
- `GET /incidents` — до 1000 последних инцидентов.
- `GET /traces/{trace_id}` — цепочка событий одного запроса.
- `GET /deployments/{service}?before=v1&after=v2` — сравнение версий.
- `GET /events/{id}` — событие и присвоенная группа.

RabbitMQ служит для уведомлений; периодический опрос PostgreSQL сохраняет
обработку при потере уведомления или временной недоступности брокера.

## Проверки

```sh
cp .env.example .env
set -a
. ./.env
set +a
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
```

Тесты используют временные схемы PostgreSQL с расширением pgvector.
Проверяются дубликаты и конфликты, перегрузка, поздние события, отсутствие
тревог на обычных сообщениях, восстановление Drain и атомарный откат состояния.
CI выполняет эти проверки и потоковую демонстрацию в Docker.

## Ограничения

Один сериализованный поток изменения Drain; модель хранит до 1000 активных
кластеров. История событий и групп автоматически не очищается. После вытеснения
старого кластера аналогичный шаблон может получить новую группу.
Лексическое сходство и Drain могут ошибочно объединять или разделять ошибки.
Правило обнаруживает новые повторяющиеся шаблоны, а не все виды аномалий.
Для известной ошибки добавлен отдельный контур сравнения релизов с нормировкой
на число запросов. Он требует явно заданных окон и счётчиков трафика.

Старый обзор `/deployments/{service}` относится ко всему набору без нормировки;
для решения о регрессии используйте `/comparisons`. Поздняя загрузка старой версии не отзывает ранее созданный
инцидент. Общий trace и временной порядок — признаки связи, но не доказательство
первопричины. Мультитенантность, редактирование групп и очистка персональных
данных в логах не реализованы. Не загружайте реальные секреты в демонстрацию.

Порты привязаны к localhost; ключ и пароли демонстрационные.
Остановка: `docker compose down`; том сохраняется.
Документация: [Drain3](https://github.com/logpai/Drain3),
[pgvector](https://github.com/pgvector/pgvector).


## Регрессии после релиза

`PUT /traffic` принимает `service`, `version`, `minute` (граница минуты с часовым
поясом), `requests` и `expected_revision` (0 для первой записи). Это окончательное
число запросов за минуту, не прибавление. Исправление требует текущей ревизии,
иначе возвращается 409. Текущее значение читается через `GET /traffic` с теми же
service/version/minute. Секретные пользовательские данные в счётчики не входят.

`POST /comparisons` принимает UUID `id`, `service`, `before_version`, `after_version`,
`before_start`, `after_start` и `minutes` от 1 до 60. Сравниваются полуоткрытые
интервалы одинаковой длительности. Повтор ID с другими параметрами — 409.
Данные о трафике должны присутствовать для **каждой** минуты обоих окон.

Воркер выявляет регрессию группы при минимум 100 запросах в каждом окне,
минимум пяти ошибках после релиза, интенсивности не ниже 0,01 ошибки на запрос
и росте минимум в три раза. Ошибок на один запрос может быть несколько: это
интенсивность, не вероятность ошибки. Порог — прозрачное операционное правило,
не статистический тест со строго контролируемой частотой ложных открытий.

`GET /comparisons/{id}` возвращает признаки решения, состояние `active` или
`retracted`, ревизию и историю изменений. Поздние логи и исправленные счётчики
автоматически помечают сравнение для повторной оценки. Если подтверждение роста
исчезло, тревога отзывается с сохранением истории. Повтор обработки тех же
данных не создаёт новую ревизию. Решения предварительные: окна можно уточнять
поздними данными. Старые оповещения `/incidents` о новых шаблонах остаются
отдельным механизмом и этой версионной семантики не имеют.

В стенде максимум 100 сравнений. Изменения логов, счётчиков и оценки согласованы
одной advisory lock PostgreSQL; атомарно сохраняются новое решение, история и
сброс признака dirty. Это ограничивает пропускную способность, но не теряет
переоценку на гонке с поступлением поздних данных.
